Kong — perímetro de seguridad único

Todo tráfico LLM pasa por Kong antes de llegar al agente. Maneja autenticación, rate limiting por cliente, PII masking en tiempo real y logging de cada token para auditoría. Es el único punto de entrada al plano de orquestación — sin Kong, no hay acceso al agente.

LangGraph + Vertex AI — cerebro compartido

LangGraph define la máquina de estados del agente: qué hacer en cada turno, cuándo escalar a humano, cómo manejar errores. Vertex AI Agent Engine corre el LLM. Responsabilidad compartida — la seguridad no está solo en el gateway ni solo en el agente.

Personal Banker — primer agente de producción

Canal de voz. Consultas de saldos y movimientos, bloqueo de tarjetas, programación de pagos, solicitud de certificados. Escala automáticamente a agente humano ante indicadores de fraude, complejidad o riesgo. SLA 99.5%, latencia máxima 3s.

BIAN como lenguaje común

Banking Industry Architecture Network define los dominios de servicio bancario. Cada MCP server se mapea a un dominio BIAN (Card Management, Payment Order, etc.). Esto garantiza que el lenguaje de las herramientas del agente sea consistente con el modelo de negocio del banco.

Arquitectura · Trade-offs Documentados

3 Decisiones Críticas

Cada decisión fue evaluada contra latencia, compliance regulatorio, blast radius y autonomía de equipos. El "depende" es el inicio del análisis, no el final.

D-01
Estado de sesión del agente conversacional
El agente de voz mantiene contexto de conversación (turno actual, intent, historial) y debe garantizar audit trail completo por regulación financiera. SLA estricto de latencia máxima 3 segundos en canal de voz.
Opciones evaluadas
OpciónVelocidadPersistenciaComplianceRiesgo
Redis solo Muy alta (<1ms) Efímera (TTL) Insuficiente Pierde trail si cae
Firestore solo Media (10-50ms) Permanente Cumple Latencia borderline
Híbrido Redis + Firestore elegida Alta (<3ms) Permanente Cumple Bajo — recuperable
Decisión y justificación
Redis maneja el estado de la sesión activa (in-flight): el contexto del turno actual, el intent detectado, las variables de la conversación. Latencia sub-3ms garantizada. Al finalizar cada turno de conversación, se escribe de forma asíncrona a Firestore para el audit trail permanente. Si Redis falla, la sesión puede recuperarse desde Firestore. Si solo usáramos Redis, perderíamos la trazabilidad regulatoria. Si solo usáramos Firestore, no cumpliríamos la latencia de voz. El costo adicional (~20% más) es insignificante frente al riesgo regulatorio.
D-02
Kong AI Gateway vs. API Gateway genérico
Toda llamada a modelos LLM debe pasar por un control centralizado de seguridad, rate limiting por cliente y logging de tokens para auditoría. El banco tendrá 200+ desarrolladores accediendo a múltiples modelos en los próximos 18 meses.
Opciones evaluadas
OpciónAI-nativePII maskingToken trackingVendor lock-in
AWS API Gateway No Manual / custom No nativo Alto (AWS)
Apigee (GCP nativo) Parcial Plugin custom Parcial Medio (GCP)
Kong AI Gateway elegida Nativo — built-in Plugin incluido Por modelo/cliente Bajo (open-core)
Decisión y justificación
Kong AI Gateway tiene plugins nativos para prompt injection detection, PII masking y token-level rate limiting — funcionalidades que un gateway genérico requeriría construir desde cero. Al ser open-core, reduce la dependencia de un proveedor cloud específico: si el banco decide mover workloads de GCP a Azure, el gateway no cambia. Kong es el único punto de entrada al plano LLM — ninguna llamada a Vertex AI o a cualquier modelo sale sin pasar por él. Esto garantiza que el 100% del tráfico AI quede auditado.
D-03
MCP Servers centralizados vs. distribuidos por dominio
Los agentes necesitan herramientas (tools) para acceder a APIs bancarias: consultar saldos, bloquear tarjetas, programar pagos. El banco tiene múltiples dominios (tarjetas, créditos, inversiones, pagos) con equipos de desarrollo independientes.
Opciones evaluadas
OpciónAutonomía equiposBlast radiusGovernanceTime-to-market
MCP centralizado Baja — cuello de botella Total — un fallo afecta todo Fácil — un equipo Lento — dependencia
MCP por dominio elegida Alta — squads dueños Controlado — aislado Requiere contrato API Rápido — paralelo
Decisión y justificación
Cada dominio de negocio publica y opera su propio MCP server. Si el MCP de tarjetas falla, los agentes de créditos siguen operando — blast radius controlado, exactamente lo que exige una superintendencia financiera en su análisis de riesgo operacional. El contrato es simple: cada MCP debe registrarse en el catalog central (ServiceNow) y cumplir el schema de herramientas estándar de la plataforma. Los equipos de negocio ganan autonomía; la plataforma mantiene governance a través del catalog, no del control directo.

Detección de model drift y hallucination

LangSmith ejecuta evals continuos sobre una muestra del 5% del tráfico real contra un golden dataset bancario. Si la tasa de respuestas incorrectas supera 0.5% en ventana de 1 hora, se dispara alerta a on-call. Si supera 2%, el agente entra en modo degradado: responde solo consultas de bajo riesgo y escala el resto a agente humano. Si el equipo no actúa en 30 minutos, el rollback al modelo anterior es automático.

Fallo en medio de una conversación activa

LangGraph implementa checkpointing de estado en Redis cada turno. Si el pod falla, el siguiente pod recupera el estado y continúa la conversación sin que el cliente lo note. Si el fallo es total (Kong down, Vertex unreachable), el canal de voz hace fallback automático a IVR clásico: "alta demanda, transfiriendo con asesor". El audit trail se escribe a Firestore antes de la transferencia.

Visibilidad al equipo de negocio — sin reportes manuales

Dashboard en tiempo real embebido en Port.io. Business owners ven: CSAT por canal, resolución en primera llamada, tasa de escalamiento, tiempo promedio de atención, top 10 intents más frecuentes. Todo actualizado en streaming desde LangFuse. No hay reunión de "dime cómo va el agente" — los datos están siempre disponibles. Las alertas de degradación van a Slack del área de negocio, no solo al equipo técnico.

Runbook P1 — agente en producción degradado

Cada incidente queda registrado en ServiceNow para auditoría regulatoria. El tiempo de respuesta y las acciones tomadas son parte del reporte de riesgo operacional.

T + 0 min
Dynatrace detecta anomalía
Latencia P95 supera 2.5s o error rate supera 1%. PagerDuty notifica al on-call en máximo 2 minutos. Se abre ticket automático en ServiceNow.
T + 5 min
Kong throttles el tráfico
Rate limiting automático al 50% de capacidad. Nuevas sesiones entran a cola de espera. Clientes activos no son interrumpidos.
T + 10 min
LangSmith identifica la causa raíz
Tracing completo de la conversación fallida. Se identifica si el problema es modelo (hallucination, drift), tool (MCP server), o infraestructura (latencia Vertex AI, Redis OOM).
T + 30 min
Decisión: rollback o fix forward
Si es modelo: rollback automático a versión anterior en ArgoCD. Si es infra: escalamiento a SRE con runbook específico. ServiceNow registra RCA y acciones para el reporte regulatorio.

Construir vs. comprar

Construir: lógica de agentes (LangGraph workflows), integraciones core banking, políticas de governance específicas del banco, golden datasets para evals de dominio financiero, dashboards de negocio.

Comprar / consumir como servicio: runtime LLM (Vertex AI — no construir un modelo propio), observabilidad (Dynatrace, LangSmith), gateway (Kong), CI/CD (GitHub Actions), IDP (Port.io). No construir lo que ya existe mejor que lo que nosotros haríamos.

Riesgos anticipados y mitigación
  • Vendor lock-in LLM: abstracción detrás de Kong — cambiar de Gemini a otro modelo es configuración, no código.
  • Adopción lenta de squads: el Golden Path debe ser irresistible — si es más fácil hacerlo solo, perdemos. Dogfood interno primero con el equipo de plataforma.
  • Regulación cambiante: ServiceNow como sistema de record — cada decisión del agente es trazable. La auditoría es un feature, no overhead.
La regulación no es un freno — es el moat. Un banco que tiene governance AI certificada puede mover más rápido que la competencia porque ya tiene la confianza del regulador. Cada restricción que cumplimos hoy es una barrera de entrada para competidores mañana.
